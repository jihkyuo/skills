# orca-handoff 스킬 설계 (2026-08-10)

> superpowers:brainstorming으로 도출, codex 크리틱(39건 중 15건 수용) 반영한 개정판. 구현은 superpowers:writing-skills로.

> **2026-09-03 개정(v0.1.4):** §3의 «참조형» 중 지식 층(mattpocock handoff 파일을 경로로 읽기)은 **발췌**로 바뀌었다 — `references/handoff-doc.md` + `NOTICE.md`(MIT, 6654f6b 고정). 이유: 이 라이브러리 원칙 1 «호출 말고 발췌», 그리고 그 스킬이 없는 환경(다른 에이전트·codex 세션)에서 폴백만 남던 문제. 환경 층의 orca-cli 참조는 그대로다(Orca 가 제공하는 스킬이라 벤더링 대상이 아니다). 아래 §3·§4.3-3·§4.4 의 해당 문장은 역사 기록으로 둔다.

## 1. 배경과 목적

핸드오프(다른 에이전트로의 소유권 이전)에는 두 개의 층이 있다:

- **환경 층** — 워크트리, 미push 커밋, 브랜치 상태. "작업하던 자리"
- **지식 층** — 논의 내용, 기각한 접근, 사용자의 구두 제약, 다음 단계. "작업하던 머릿속"

현재 자산은 두 층에 하나씩 있으나 서로 연결돼 있지 않다:

| 자산 | 층 | 형태 | 한계 |
|---|---|---|---|
| 오르카 핸드오프 방식 (사용자 커스텀) | 환경 | 특정 프로젝트의 **메모리** | 다른 프로젝트에서 회상 안 됨. 매번 "메모리 확인해라" 설명 필요 |
| mattpocock `handoff` 스킬 (다운로드) | 지식 | 전역 스킬, `disable-model-invocation: true` | AI가 Skill 도구로 호출 불가. 환경 층 없음 |

**목적**: 두 층을 하나의 전역 스킬로 묶어, 어느 프로젝트에서든 "핸드오프해줘" 한마디로 완전한 핸드오프가 실행되게 한다.

## 2. 성공 기준

1. 아무 프로젝트에서나 "핸드오프해줘" → 스킬이 발동해 지식 문서 생성 + 환경 인계 + 전달 확인까지 수행한다. 사용자가 메모리나 절차를 설명할 필요가 없다. (갈래 판별이 애매할 때의 확인 질문 1회는 예외 — 오판이 확인보다 비싸다.)
2. 두 절차 정본(mattpocock·orca-cli)의 **복제본을 두지 않아** 업스트림 갱신 시 드리프트가 생기지 않는다. 자동 호환을 보장한다는 뜻이 아니다 — 업스트림이 깨진 형태로 바뀌면 인라인 폴백으로 동작하고 사용자에게 알린다.
3. 진행 중 작업을 독립 워크트리로 넘겨 브랜치 맥락이 새 세션에서 안 보이게 되는 실수, 프롬프트 미제출 상태로 방치하는 실수가 스킬 단계에서 차단된다.

## 3. 구조 결정: 참조형 단일 스킬

판단 로직(갈래 판별·읽기 순서·전달 확인)은 이 스킬이 소유하고, 두 절차 정본은 참조한다.

**기각한 대안**
- *전부 인라인(자기완결형)*: mattpocock이 redaction 규칙을 강화해도 인라인 사본은 낡은 채 남아, 외부 모델(codex 등) 핸드오프에 PII가 실릴 수 있다. "제3의 정본" 드리프트 문제.
- *얇은 라우터(메모리 지시형)*: 메모리는 프로젝트 스코프라 다른 레포에서 빈손이 된다. 이 설계의 출발점이 된 문제 그 자체.

## 4. 스킬 명세

### 4.1 이름·위치

- 이름: `orca-handoff`
- 위치: `~/.claude/skills/orca-handoff/SKILL.md` (전역)
- 관리: 수동 소유(커스텀 스킬). skills CLI·플러그인 관리 밖.

### 4.2 frontmatter와 라우팅 규칙

```yaml
---
name: orca-handoff
description: >-
  진행 중 작업 또는 새 작업을 다른 에이전트에게 완전히 넘기는(소유권 이전)
  핸드오프 절차 — 지식 문서 생성과 환경(워크트리) 인계를 모두 수행한다.
  "핸드오프", "인수인계", "이 작업 다른 에이전트/워크트리로 넘겨", "handoff",
  "handover" 의도에 사용. 문서 생성만 원하는 요청("핸드오프 문서만 만들어줘")도
  이 스킬이 받아 문서 단계만 수행한다. 단 사용자가 /handoff나 orca-cli 등 특정
  스킬을 명시하면 그 스킬이 우선한다. 넘긴 뒤 지켜보며 조율(폴링·완료 대기·task
  DAG)까지 원하는 요청이면 이 스킬이 아니라 orchestration — 섞여 있으면 묻는다.
---
```

`disable-model-invocation`은 넣지 않는다 — 자동 발동이 이 스킬의 존재 이유다.

라우팅 원칙(본문 서두에도 명시): **사용자의 명시 호출이 항상 이긴다.** 설명 문구 기반 라우팅은 확률적이므로, 경합 스킬(/handoff·orca-cli·orchestration)과의 경계는 위 문구 + 구현 후 라우팅 테스트(§6)로 잡는다.

### 4.3 본문 5단계

1. **원칙** — 핸드오프 = 소유권 이전. 프롬프트 전달·확인 후 이 세션은 감시를 멈추고, **해당 워크트리에서 작업을 계속하지 않는다**(두 에이전트 동시 편집 방지). 지켜보며 조율할 거면 이 스킬이 아니라 orchestration.
2. **갈래 판별** — 미push 커밋, **미커밋 변경(untracked 포함)**, 또는 기존 브랜치에서 이어야 할 맥락이 있으면 **같은 워크트리에 새 터미널**. 완전히 새 작업이면 **독립 워크트리**(`--no-parent`). 애매하면 자동 판정하지 않고 사용자에게 묻는다.
   - 위험의 정확한 서술: 커밋 자체는 git 객체로 남지만, **새 워크트리는 origin/main에서 갈라지므로 그 브랜치의 미push 커밋·미커밋 변경이 새 세션의 시야에 없다.** 근거 사례: 사례 A — 브랜치에 미push 50커밋, 독립 워크트리를 팠으면 새 세션이 그 전부를 못 봤다.
3. **지식 층** — `~/.claude/skills/handoff/SKILL.md`(mattpocock)를 **읽고 그 절차를 따라** 대화 압축 문서를 OS 임시 디렉토리에 만든다(`disable-model-invocation`은 Skill 도구 호출만 막을 뿐 파일 읽기는 제한하지 않는다). **사용자가 밝힌 다음 세션의 목적·지시를 mattpocock 절차의 인자(argument)로 삼아 문서를 그 목적에 맞춰 재단한다.**
   - 파일이 없으면 인라인 폴백: 기각한 접근·사용자의 구두 제약·다음 단계·suggested skills를 담고, 산출물(스펙·커밋·diff)은 경로 참조만, 비밀값·PII는 삭제해 임시 디렉토리에 저장. 재설치를 한 줄 안내.
   - 레포에 좌표 문서 규약이 있으면(프로젝트 메모리·AGENTS.md가 알려줌) **그 레포의 규약이 정한 방식대로만** 갱신·커밋한다 — 이 스킬이 새로운 쓰기 권한을 만들지 않는다. 역할 구분: 좌표 문서 = 레포에 남는 durable 상태, 핸드오프 문서 = 대화 층 휘발성 지식. 내용이 겹치면 핸드오프 문서에는 싣지 않고 좌표 문서의 해당 위치를 참조로 적는다.
4. **환경 층** — **orca-cli 스킬을 Skill 도구로 호출해** 그 규약(CLI resolve·live help로 서브커맨드 확인·앱 상태 확인)을 로드한 뒤, **한 단계** `--command` 프롬프트로 터미널을 만들고 **`--json` 응답의 터미널 ID를 보관**해 5단계 확인에 쓴다. 형태 예시(실행 전 live help로 확인):
   ```
   orca terminal create --worktree path:<현재 워크트리> --title "<인수 제목>" \
     --command "claude --model <현재 모델> --permission-mode auto '<프롬프트>'" --json
   ```
   - 프롬프트는 **한두 줄의 경로 안내로 유지**한다(컨텍스트는 문서가 든다는 원리 + 따옴표·멀티라인·특수문자로 인한 인자 파손 회피). 읽기 순서: ① 레포 AI 지침 정본(AGENTS.md 등 — 새 세션은 레포 규약을 처음 본다) ② 핸드오프 문서(임시 경로) ③ 좌표 문서 항목.
   - 스폰 에이전트 기본값은 현재와 같은 claude 모델. 사용자가 "codex한테 넘겨"처럼 지정하면 그쪽 — 실행 명령은 live help와 해당 CLI 관행으로 확인하고, 확신 없으면 명령 형태를 사용자에게 보여주고 확인받는다.
   - 두 단계(create 후 send)로 갈 수밖에 없으면 `terminal send ... --enter`를 쓴다.
5. **전달 확인** — 보관한 터미널 ID로 `terminal read` 1회. 상대가 돌기 시작했는지(토큰 소비·도구 호출) 본다. **막 떴다면 짧은 간격을 두고 1회만 재확인**(상한 2회 — 시작 확인이지 폴링·감시가 아니다).
   - 미제출 판별(claude CLI 전용 휴리스틱): `❯` 뒤에 프롬프트가 그대로 보이고 비용 $0.00. 다른 CLI를 스폰했다면 이 판별법을 적용하지 말고 출력에 프롬프트 처리 흔적이 있는지로 판단.
   - 미제출이면 `terminal send --enter`로 1회 재제출 → 재확인. 그래도 미기동이면 **터미널 상태·시도 내역을 사용자에게 보고하고 멈춘다**(터미널은 정리하지 않고 남긴다 — 증거 보존).
   - 근거 사례: 사례 B — `--enter` 누락으로 글자만 입력창에 앉아 있었고 사용자가 한참 뒤 발견. 소유권 이전은 상대가 받았을 때 성립한다.

### 4.4 실패 처리

- **orca CLI 부재·앱 미기동·상태 이상**: orca-cli 스킬의 상태 확인 절차(`status --json` 등)가 판별한다. 환경 층 불가면 지식 문서까지만 만들고 경로를 알린 뒤 멈춘다.
- **mattpocock 스킬 파일 없음**: 4.3-3 인라인 폴백.
- **부분 실패(터미널 생성됨 + 프롬프트 미제출)**: 4.3-5의 재제출 1회 → 실패 시 보고·중단. 성공처럼 보고하지 않는다 — 최종 보고는 층별(지식/환경/확인) 상태를 구분해 전한다.

### 4.5 스킬이 하지 않는 것

- 감시·폴링·완료 대기 (orchestration의 영역)
- 레포 특이 규약(브랜치 개명, 좌표 문서의 구체 위치 등) 하드코딩 — 각 프로젝트의 메모리·AGENTS.md 몫. 스킬은 "있으면 따르라"고만 한다.
- 새로운 쓰기 권한 창출 — 레포에 쓰는 건 그 레포 규약이 이미 허용하는 방식뿐.
- 세션 정리 — 사용자 몫으로 남긴다(물어보되 떠안지 않는다).

## 5. 기존 메모리 처분

`handoff-same-worktree-new-terminal` 메모리는 "정본이 `orca-handoff` 스킬로 이관됨" 포인터로 축약한다. Why 사례(A·B)는 4.3에 이관됐다. socratic과 같은 "정본은 전역, 나머지는 포인터" 패턴.

단, **프로젝트 특이 정보는 축약 후에도 메모리에 남긴다** — 이 레포의 좌표 문서 위치(원 프로젝트의 좌표 문서)가 그것이다. 스킬 4.3-3의 "좌표 문서 규약이 있으면"이 이 메모리를 통해 채워진다. 방법(전역 스킬)과 좌표(프로젝트 메모리)의 분업.

## 6. 검증 방법

1. writing-skills 절차의 서브에이전트 테스트 — 스킬만 읽은 새 에이전트가 절차를 오해 없이 수행하는지.
2. 라우팅 테스트 — 다음 문구들이 올바른 목적지로 가는지 지상 검증(스킬 파일들만 읽고 판단):
   - "핸드오프해줘" → orca-handoff
   - "핸드오프 문서만 만들어줘" → /handoff(문서만) 성격 — orca 터미널 만들지 않음
   - "orca terminal create 어떻게 써?" → orca-cli
   - "/handoff" 명시 호출 → mattpocock handoff
   - "codex한테 넘기고 끝나면 알려줘" → 감시 결합 — 확인 질문 발생
3. 실전 리허설 — 다음 실제 핸드오프 1회에서 검증하고, 발견된 지뢰는 스킬 본문에 반영. (같은 워크트리·독립 워크트리·실패 경로 전수는 실전 누적으로 커버 — 파괴적 통합 테스트를 미리 만들지 않는다.)
