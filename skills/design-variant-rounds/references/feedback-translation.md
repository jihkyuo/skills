# 피드백 번역표 — 사용자 문장이 어느 엔진으로, 워커에게 무엇이 가나

원칙: **사용자 문장은 원문으로 간다.** 코디가 하는 번역은 «어느 엔진인가»와 «어떤 절차 포인터를 붙이나»뿐이다. 수정 목록·상한 숫자·픽셀 기준·훅 요구로 바꾸는 순간 작가는 디자이너에서 패처가 되고, 변형은 코디의 해석 하나로 수렴한다.

| 사용자 문장의 꼴 | 엔진 | 워커에게 가는 것 | 코디가 만들지 않는 것 |
|---|---|---|---|
| «X가 좋다. 여기가/이것만 아쉽다» | 피드백(같은 작가) | 원문 + 킵 목록(리뷰 §6) + polish 원칙: **정제는 정체성·행동·문구·범위 밖을 보존한다. 개념이 틀렸으면 재설계지 절충이 아니다** | 수정 목록, «이 밖은 그대로» 동결 조문, 픽셀 게이트 |
| «너무 복잡하다·많다·정신없다·왜 다 보여주나» | 피드백(같은 작가) | 원문 + distill 4문: 주 목표 하나는? 필수 vs 있으면 좋은 것은? 뺄·숨길·합칠 것은? 20%로 80%를 주는 것은? + quieter 4축(색 채도·시각 무게·단순화·모션) | 밀도 상한 숫자(글자 수·잎 수·상자 수), «한 화면 한 사람» 같은 신규 금지 조문 |
| «심심하다·평범하다·AI 티» | 피드백(같은 작가) | 원문 + bolder: 대담함은 **한 곳**에, 나머지는 조용히 | 반제네릭 블랙리스트 추가 |
| «셋 다/전부 아니다. 완전 새로» | 발산(새 작가, 백지) | `thesis-divergence.md`로 만든 새 배정표 + 원문(문제 재프레이밍의 재료로) | 기존 벌의 사본·부분 재활용, 지적을 뒤집은 금지 조문(«한 줄 금지»류) |
| «A의 X와 B의 Y를 합치면» | 수렴(코디 직접) | 코디가 조합 1안을 직접 짓고 킵 안들과 나란히 | 워커 재디스패치 |
| «이 버튼/문구/간격이» | 디테일(코디 직접 + 실시간 왕복) | 한 항목 수술 → 스크린샷 → 확인 | 병렬 워커 |
| «원래 이랬어?» | 질문 | 커밋 diff로 사실을 답하고 방향을 받는다 | 원복 |
| 상태 있는 요소의 캡처 지적 | 판별 먼저 | «이 캡처가 호버 상태인가요?» 한 줄 | 디폴트로 오독한 수정 |

## 피드백 라운드 task spec에 «절차 포인터»를 붙이는 법

포인터는 한 줄이다. 예: «사용자 원문 아래에 distill 4문에 대한 네 답을 적고 나서 고쳐라.» 절차 본문을 씨드에 다시 쓰지 않는다. 워커는 이 파일을 읽을 수 있다.

## 라운드 유형 판정에서 헷갈리는 경우

- 킵 하나 + «새 컨셉도 보고 싶다» → 두 트랙을 **분리**한다: 킵의 작가는 피드백 라운드, 새 컨셉은 발산 라운드(백지·새 배정표). 킵의 사본을 새 컨셉의 출발점으로 주지 않는다.
- «전부 반려»인데 시간이 없다 → 그래도 발산이다. 사본 재활용은 시간을 줄이지 않고 라운드를 하나 더 태운다(실측: 사본 라운드 2회 연속 «고만고만», 3회째 «퇴보» 기각).
- 사용자가 구체 값을 말했다(«팝오버 372») → 그 값은 원문의 일부로 전달한다. 코디가 값을 «계약»으로 승격하지 않는다.
