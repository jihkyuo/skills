# 브리프 템플릿 — 코디네이터가 라운드 착수 때 쓰는 것

브리프는 **의도**를 적는 문서다. CSS 값·색상 헥스·«미니멀/브루탈» 같은 미적 레인은 묻지도 적지도 않는다. 조형은 워커의 몫이고, 그것을 코디가 정하는 순간 변형은 코디의 안 N벌이 된다. 브리프를 사용자에게 보여 확인 또는 한 번의 정정을 받은 뒤 **멈춘다**. 브리프 단계는 코드도 방향 계약도 쓰지 않는다.

## 브리프 7항 (설정된 과제는 3~5개 불릿, 모호·다화면·독립 기획만 전체 구조)

1. **일과 사용자** — 누가, 어떤 상황·마음 상태로 이 화면에 오나. 방문 모드(제품 UI는 «과제 수행»).
2. **성과와 증거** — 주 과제·행동, 성공의 모습, 실데이터, 이 제품에만 참인 사실.
3. **선택된 방향** — 시각 권위(디자인 시스템·토큰 실값), 구조·상호작용의 논제, 순서, 초점 순간. 발산 라운드에서는 이 항이 «논제 배정표»가 된다(`thesis-divergence.md`).
4. **범위와 경계** — 충실도(탐색/프로덕션급/전체 흐름), 폭, 상호작용 정도, 대상 이름, 건드리지 않는 것, 명시적 반목표.
5. **상태와 범위** — 실데이터의 최소·보통·최대(긴 제목·항목 10+·빈 상태·실패), 중요한 상태 전이.
6. **상호작용과 레이아웃** — 위계·토폴로지·반응·어포던스·피드백·전이. 의도로 적고 CSS로 적지 않는다.
7. **제약과 열린 결정** — 플랫폼·접근성·현지화·재사용 부품, 그리고 «워커가 지어내면 안 되는 선택»(사용자에게 되물을 것).

## 씨드팩과의 결합

브리프 7항은 `_seed/seed.md`의 머리가 된다. 그 아래 기존 씨드 절이 따른다: 토큰 실값 · 목 데이터 · 도메인 규칙 · 공통 계약(기계 검사 대상) · 크롬 마커 블록 · 실동작 목록 · 워커 로드 순서.

## 묻는 법 (사용자와의 왕복)

- 한 번에 관련 질문 2~3개, 그리고 기다린다. 한 번이 기본, 답이 큰 구멍을 드러낼 때만 두 번째.
- 정해진 사실을 다시 묻거나 뻔한 사실을 메뉴로 만들지 않는다. 그럴듯한 읽기를 단언하고 정정을 청한다.
- 첫 왕복 질문 후보: 이 화면이 풀어야 하는 문제는? 누가 어떤 상태로 오나? 그들이 이해·수행해야 할 한 가지는? 이 제품에만 참이라 이웃 제품이 못 쓰는 것은?
- 두 번째 왕복(필요할 때만): 실데이터 범위, 중요한 상태, 충실도, 손대면 안 되는 것, 구속 제약.

## 브리프가 아닌 것

- 결함 수정 목록(그건 리뷰 템플릿의 자리이고, 피드백 라운드에서도 원문이 우선한다).
- 픽셀·밀도·훅 요구 같은 게이트(게이트는 Phase 3의 R1 세트에서 늘지 않는다).
- 코디가 그린 스케치를 «참고»로 붙이는 것(스케치는 곧 뼈대 상속이다).
