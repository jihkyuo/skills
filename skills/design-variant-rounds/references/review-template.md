# 리뷰 템플릿 — 수령 판정 `review-<slot>-v1.md`

리뷰는 **판정과 증거**다. 구조·축·조형을 지시하는 문장은 넣지 않는다(그건 작가의 몫이고, 넣는 순간 변형이 코디의 안으로 수렴한다). 사용자 지적을 대신 번역하지도 않는다. v2 요구는 5개 이하, 이슈마다 «왜 사용자에게 해로운가» 한 줄.

```markdown
# review-<slot>-v1 — <슬롯 이름> · 라운드 N

## 0. 결론 한 줄
통과 / 반려(근거 절 번호) · v2 요구 개수

## 1. 계약 (기계) — 하나라도 실패 = 반려
- check(외부 요청 0 · 크롬 블록 해시 · 어휘·금지 문구): PASS/FAIL 근거
- detect.mjs(무시 목록 적용 후): N건 — 읽고 남긴 것만 적는다
- 모션 grep(motion-decisions.md): 매치와 판정

## 2. 실동작 (씨드 §실동작 ①~⑨) — 실클릭, 전/후를 눈으로
| # | 동작 | 결과 | 근거(캡처·계측) |

## 3. 휴리스틱 0~4 (해당 없으면 n/a, 합계는 채점한 항목 ×4 기준)
| 휴리스틱 | 점수 | 핵심 이슈 |
| 1 시스템 상태 가시성 | | |
| 2 현실 세계와의 일치(사용자 언어) | | |
| 4 일관성·표준 | | |
| 5 오류 예방 | | |
| 6 인식 > 회상 | | |
| 8 미니멀(모든 요소가 자리를 번다) | | |
| 9 오류 인지·회복 | | |
(3 사용자 통제, 7 유연성, 10 도움말은 목업 기본 n/a — 흐름이 있으면 채점)
4 = 정말 훌륭. 실제 화면 대부분은 20~32/40.

## 4. 인지부하 8항 (실패 수: 0~1 낮음 · 2~3 보통 · 4+ 심각)
- [ ] 단일 초점  - [ ] 청킹(묶음 ≤4)  - [ ] 그룹핑  - [ ] 시각 위계
- [ ] 한 번에 하나  - [ ] 선택지 ≤4  - [ ] 작업기억(앞 화면을 기억해야 하나)  - [ ] 점진적 노출

## 5. 디자인 특정성
이 구성·상호작용·시각 언어가 이 제품에 뿌리를 두었나, 무관한 제품이 그대로 써도 되나. 검출기 결과를 보기 전에 판단한다.

## 6. 강점 2~3 (동결 후보 — 다음 판에서 건드리지 말 것)
-

## 7. 우선 이슈 3~5 (P0 막힘 · P1 큰 혼란 · P2 우회 가능 · P3 광택)
- [P?] 무엇 — 왜 사용자에게 해로운가 — 근거(캡처·줄)
«고객이 지원팀에 연락할 문제인가»가 예이면 P1 이상.

## 8. 재스킨 판정 (발산 라운드만)
다른 슬롯과 나란히 놓고 «완전 다른 변형인가». 헤드라인 교환 테스트(round-rules.md §6). 텍스트 유사도 수치는 근거가 아니다.

## 9. v2 요구 (우선순위순, ≤5)
1.
```

## 코디가 이 문서에 쓰지 않는 것

- «~를 ~로 바꿔라» 식 조형 지시(간격 값·폭·위치). 이슈와 해로움만 적고 해법은 작가에게.
- 다른 슬롯과 «같은 표현»을 이유로 한 변경 요구. 차이는 축에서 나오지 요소 단위 상이성에서 나오지 않는다.
- 사용자 피드백의 요약·재해석. 피드백은 Phase 4에서 원문으로 따로 간다.
